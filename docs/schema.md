# Supabase schema

This document is the source of truth for the remote Postgres model. The initial
implementation is in
`supabase/migrations/20260811000100_initial_schema.sql`.

## Conventions

- Every application row is owned by exactly one authenticated user. `public.users`
  uses `id = auth.uid()`; every other table carries `user_id`.
- IDs are UUIDs generated by the client for offline writes. Postgres also provides
  `gen_random_uuid()` as a fallback.
- `created_at` is the creation timestamp, `updated_at` is the server mutation
  timestamp maintained by a trigger, and `client_updated_at` is the client-supplied
  logical timestamp used by last-write-wins sync. Sync compares
  `client_updated_at`; it must not use `updated_at` for conflict resolution.
- The shared update trigger returns the existing row when an incoming
  `client_updated_at` is older. This prevents a delayed offline queue item from
  replacing a newer logical write; `updated_at` remains server-controlled.
- User-visible deletion is a soft delete: set `deleted_at` and enqueue that tombstone.
  Authenticated clients intentionally receive no hard-delete policy. A privileged
  maintenance process may purge old tombstones later.
- Sensitive fields (diet, sleep, injury, and AI context) remain private under RLS.
  Do not copy them into logs or analytics payloads. Edge Functions must verify
  `users.ai_data_consent` before sending any context to an AI provider.
- Cross-table foreign keys include `user_id`. This prevents an owned child row from
  pointing at another user's parent row even if a client submits a forged UUID.
- All weights are stored as a numeric value plus `load_unit`. The progression engine
  converts to one canonical unit before calculating volume; no estimated 1RM is
  stored or calculated.
- Flexible user-authored categories (equipment, muscle groups, injury flags) use
  text arrays or JSON. Workflow states with a stable closed vocabulary use enums.

## Tables

### `users`

One private application profile per Supabase Auth user. A trigger creates the row
when `auth.users` receives a new account, and the migration backfills any existing
accounts.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | PK and FK to `auth.users(id)` |
| `display_name` | `text` | Optional |
| `timezone` | `text` | IANA timezone, defaults to `UTC` |
| `preferred_load_unit` | `load_unit` | `kg` or `lb` |
| `training_experience` | `experience_level` | Optional until onboarding completes |
| `available_equipment` | `text[]` | User-authored equipment keys |
| `injury_flags` | `jsonb` | JSON array; sensitive |
| `goals` | `fitness_goal[]` | Composition, strength, both, or general wellness |
| `typical_diet_pattern` | `text` | Optional onboarding context; sensitive |
| `ai_data_consent` | `boolean` | Explicit AI processing consent |
| `ai_data_consented_at` | `timestamptz` | Required while consent is true |
| `medical_disclaimer_acknowledged_at` | `timestamptz` | First-AI-use acknowledgement |
| common timestamps | `timestamptz` | `created_at`, `updated_at`, `client_updated_at` |

The profile is deleted automatically when the Auth user is deleted. Revoking AI
consent does not erase history automatically; it prevents new client-side AI thread
or message inserts and must prevent new Edge Function provider calls.

### `exercises`

The user's exercise catalog. `movement_pattern`, primary/secondary muscle groups,
equipment, target rep range, and load increment supply deterministic double
progression without encoding 1RM concepts. Built-in starter exercises are copied
into each user's catalog, rather than exposed as global RLS exceptions.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id` | `uuid` | Client-generated PK; owning profile FK |
| `name` | `text` | Required display name |
| `movement_pattern` | `text` | Stable app key such as `horizontal_push` |
| `primary_muscle_group` | `text` | Primary volume bucket |
| `secondary_muscle_groups` | `text[]` | Optional secondary volume buckets |
| `equipment` | `text` | Optional user-authored equipment key |
| `target_rep_min`, `target_rep_max` | `smallint` | Positive double-progression range |
| `load_increment` | `numeric(8,2)` | Positive next-load increment |
| `notes` | `text` | Optional technique or accommodation notes |
| `is_archived` | `boolean` | Hidden from new selection but retained in history |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `workouts`

A planned or performed session. `performed_on` is the user's local calendar day;
`started_at` and `completed_at` retain absolute times. Status is one of `planned`,
`in_progress`, `completed`, or `skipped`.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id` | `uuid` | PK and owner FK |
| `title` | `text` | Required; defaults to `Workout` |
| `status` | `workout_status` | Session workflow state |
| `performed_on` | `date` | User-local reporting day |
| `started_at`, `completed_at` | `timestamptz` | Optional absolute session times |
| `notes` | `text` | Optional session notes |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `sets`

An ordered set inside a workout and exercise. Reps, load, optional RPE, set kind,
and completion time are stored as observations. `workout_id + user_id` and
`exercise_id + user_id` are composite foreign keys. Active rows have a unique
`(workout_id, sort_order)`.

The client counts `working` sets for default volume calculations. Warm-up, drop,
and failure sets remain available for history but must be included only by an
explicit progression rule.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id` | `uuid` | PK and owner FK |
| `workout_id`, `exercise_id` | `uuid` | User-scoped parent FKs |
| `sort_order` | `integer` | Zero-based order, unique within an active workout |
| `kind` | `set_kind` | `working`, `warmup`, `drop`, or `failure` |
| `reps` | `smallint` | Positive completed reps |
| `load_value`, `load_unit` | `numeric`, `load_unit` | Non-negative observed load and `kg`/`lb` |
| `rpe` | `numeric(3,1)` | Optional value from 1 through 10 |
| `completed_at` | `timestamptz` | Absolute completion time |
| `notes` | `text` | Optional set notes |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `meals`

A meal header with local meal time, optional meal type, notes, and provenance.
Photo-assisted meals can retain a private Storage path, typed context, and an
offline-safe AI processing state (`not_requested`, `pending`, `processing`,
`completed`, or `failed`). Storage objects require their own bucket policies; a
path in this table is not public access authorization.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id` | `uuid` | PK and owner FK |
| `name`, `type` | `text`, `meal_type` | Display name and optional meal category |
| `eaten_on`, `eaten_at` | `date`, `timestamptz` | User-local reporting day and absolute time |
| `source` | `meal_source` | `manual`, `ai_photo`, or `imported` |
| `notes` | `text` | Optional user notes |
| `photo_storage_path` | `text` | Optional private Storage object path |
| `ai_context` | `text` | Optional typed context accompanying a photo |
| `ai_status`, `ai_error_code` | enum, `text` | Queue state and machine-readable failure code |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `food_items`

Line items belonging to a meal. Each row stores the entered portion, calories,
protein, carbohydrate, fat, and optional fibre. AI-derived items can include a
0-to-1 confidence score. Meal totals are derived from active food items so a second
stored total cannot drift.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id`, `meal_id` | `uuid` | PK, owner FK, and user-scoped meal FK |
| `sort_order` | `integer` | Non-negative display order |
| `name` | `text` | Required food name |
| `quantity`, `unit` | `numeric`, `text` | Positive entered portion |
| `calories_kcal` | `numeric(10,2)` | Non-negative energy estimate |
| `protein_g`, `carbohydrate_g`, `fat_g` | `numeric(10,2)` | Non-negative macros |
| `fibre_g` | `numeric(10,2)` | Optional non-negative fibre |
| `source` | `meal_source` | Entry provenance |
| `confidence` | `numeric(4,3)` | Optional AI confidence from 0 through 1 |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `nutrition_targets`

Historical daily macro targets, effective from a local date and optionally through
another local date. The source is `manual` or `adaptive`. Clients select the latest
active row for a date. Adaptive target logic arrives later, but Phase 1 can already
display and preserve manual targets without overwriting history.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id` | `uuid` | PK and owner FK |
| `effective_from`, `effective_to` | `date` | Inclusive effective range; end may be null |
| `calories_kcal` | `numeric(10,2)` | Positive daily energy target |
| `protein_g`, `carbohydrate_g`, `fat_g` | `numeric(10,2)` | Non-negative daily macro targets |
| `fibre_g` | `numeric(10,2)` | Optional non-negative daily fibre target |
| `source` | `nutrition_target_source` | `manual` or `adaptive` |
| `rationale` | `text` | Optional plain-language reason for a change |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `wellness_logs`

Timestamped subjective or imported context. Supports free text, mood, energy,
stress, soreness, motivation, sleep duration/quality, body weight, and structured

future HealthKit or Health Connect imports.

| Column | Type | Notes |
| --- | --- | --- |

| `kind` | `text` | Required log category, kept extensible |
| `logged_on`, `logged_at` | `date`, `timestamptz` | User-local reporting day and absolute time |
| `source` | `wellness_source` | Manual, HealthKit, or Health Connect |
| `mood_score`, `energy_score`, `stress_score` | `smallint` | Optional 1-5 scores |
| `soreness_score`, `motivation_score` | `smallint` | Optional 1-5 scores |
| `sleep_duration_minutes` | `integer` | Optional value from 0 through 1440 |
| `sleep_quality_score` | `smallint` | Optional 1-5 score |
| `body_weight_kg` | `numeric(7,3)` | Optional positive canonical weight |
| `injury_flags` | `jsonb` | JSON array; sensitive |
| `notes` | `text` | Optional free-form check-in; sensitive |
| `metadata` | `jsonb` | JSON object for source-specific values |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `ai_conversations`

AI thread metadata only: purpose, title, status, and last-message timestamp. It does
not duplicate the full message stream.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id` | `uuid` | PK and owner FK |
| `purpose` | `text` | Extensible purpose, defaults to `wellness` |
| `title` | `text` | Optional user-visible title |
| `status` | `ai_conversation_status` | `active` or `archived` |

### `ai_messages`

Normalized messages within an AI conversation. `content` holds rendered text;
`structured_content` optionally holds machine-readable estimates or explanation
metadata. Client RLS permits inserts only for the `user` role and only while AI data
consent is active. Client updates are likewise limited to user-role messages.
Assistant/system/tool messages must be written and changed by a trusted Edge
Function. Existing messages remain readable after consent is revoked so offline
history does not disappear.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id`, `conversation_id` | `uuid` | PK, owner FK, user-scoped thread FK |
| `sequence` | `integer` | Non-negative and unique within a thread |
| `role` | `ai_message_role` | User, assistant, system, or tool |
| `content` | `text` | Renderable text; may be blank only with structured content |
| `structured_content` | `jsonb` | JSON object for typed results |
| `metadata` | `jsonb` | JSON object for non-secret message metadata |
| `model`, `provider_message_id` | `text` | Optional provider audit identifiers |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

### `notification_preferences`

One row per user and contextual notification type. Preferences include an enabled
flag, quiet hours, timezone, minimum interval, last-notified timestamp, and a JSON
object for trigger-specific thresholds. All notification types default disabled;
there is no blanket retention reminder type.

| Column | Type | Notes |
| --- | --- | --- |
| `id`, `user_id` | `uuid` | PK and owner FK |
| `type` | `notification_type` | Contextual trigger; unique per user |
| `enabled` | `boolean` | Defaults false; explicit opt-in only |
| `quiet_hours_start`, `quiet_hours_end` | `time` | Optional local quiet-hours window |
| `timezone` | `text` | IANA timezone used for scheduling |
| `minimum_interval_minutes` | `integer` | Non-negative trigger cooldown |
| `last_notified_at` | `timestamptz` | Last successful delivery time |
| `conditions` | `jsonb` | Trigger-specific threshold object |
| sync columns | timestamps | `created_at`, `updated_at`, `client_updated_at`, `deleted_at` |

## Row Level Security

RLS is enabled and forced on every table. Authenticated users may select, insert,
and update only their own rows. `users` compares `id` with `auth.uid()`; all other
tables compare `user_id`. There are deliberately no authenticated delete policies,
so deletions sync as tombstones.

`ai_conversations` and user-role `ai_messages` add a consent check on insert.
Anonymous access is revoked. The Supabase service role retains its normal RLS bypass
for trusted migrations, retention jobs, and Edge Functions; it must never be exposed
to the client.

## Indexing and sync queries

Each high-volume table has an owner/time index for timeline reads and an
`(user_id, client_updated_at)` index for incremental sync. Child lookup indexes cover
workout sets, exercise history, meal items, and conversation messages. Timeline
indexes exclude soft-deleted rows where appropriate.

Typical pull query semantics are:

```sql
select *
from public.workouts
where user_id = auth.uid()
  and client_updated_at > :last_pulled_client_timestamp
order by client_updated_at, id;
```

The production sync implementation should use a stable cursor containing both
`client_updated_at` and `id`, tolerate client clock skew, and advance its cursor only
after committing the local SQLite transaction.

## Migration rules

1. Update this document before or alongside every table change.
2. Enable and force RLS in the same migration that creates a table.
3. Add owner policies and explicit role grants in that migration.
4. Use user-scoped composite foreign keys for new owned relationships.
5. Preserve soft-delete tombstones and the dual timestamp convention.
6. Never store API keys, OAuth refresh tokens, or Supabase service credentials here.
