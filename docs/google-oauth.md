# Google OAuth configuration

JIEN uses Supabase Auth as the OAuth broker. Google and JIEN therefore have two different redirect settings; they are not interchangeable.

## Required redirect chain

1. Google Cloud's OAuth web client must authorize the callback shown in **Supabase Dashboard > Authentication > Sign In / Providers > Google**. It has this form:

   `https://<project-ref>.supabase.co/auth/v1/callback`

2. Supabase's redirect URL allow list must contain JIEN's deployed callback:

   `https://jien-coral.vercel.app/?auth_callback=1`

3. JIEN receives a short-lived Supabase PKCE code and exchanges it with the verifier stored before the redirect. JIEN must never exchange Google's provider code, whose value commonly starts with `4/`.

Do not put the Google client secret in the repository or Expo public environment variables. It belongs only in the Supabase Google provider configuration.

## `Unable to exchange external code`

This message is generated by Supabase Auth while it is exchanging Google's provider code, before JIEN receives a Supabase PKCE code. If it appears after Google consent:

1. In Google Cloud, open the same OAuth 2.0 **Web application** client whose client ID is configured in Supabase.
2. Confirm its authorized redirect URI is the Supabase `/auth/v1/callback` URL shown by the Supabase Google-provider panel, not JIEN's application callback URL.
3. Create or reveal a valid client secret for that same client, then copy it into Supabase's **Client Secret (for OAuth)** field and save.
4. Start a new sign-in attempt. Provider codes are single-use; refreshing the failed callback cannot recover it.

JIEN redacts the raw provider code from its error UI and leaves local data unchanged when this server-side exchange fails.

## Google Sheets export

Google Sheets export uses a separate browser OAuth token flow because the source data
is local SQLite data and does not need to pass through JIEN's backend. The browser calls
the Drive and Sheets REST APIs directly. It requests exactly this scope:

`https://www.googleapis.com/auth/drive.file`

That scope lets JIEN find and update only files created through this OAuth client. Do
not replace it with the broad `drive` scope. The short-lived access token remains in
memory for the export request; it is never written to SQLite, browser storage,
Supabase, the repository, or an Expo public environment variable.

### One-time Google Cloud setup

1. In the Google Cloud project used for JIEN, enable both **Google Sheets API** and
   **Google Drive API**.
2. Open **Google Auth Platform > Data Access** and add the non-sensitive
   `.../auth/drive.file` scope to the OAuth consent screen. Do not add `.../auth/drive`.
3. Create or reuse an OAuth 2.0 **Web application** client. Add the deployed JIEN
   origin, currently `https://jien-coral.vercel.app`, under **Authorized JavaScript
   origins**. Add the local web origin when testing locally.
4. Set that web client's public ID as `EXPO_PUBLIC_GOOGLE_DRIVE_CLIENT_ID` in the
   Vercel project and local development environment. This value is a public client ID,
   not a client secret. Never add the client secret to an Expo public variable.

The existing Supabase Google sign-in redirect chain above remains unchanged. Sheets
export uses Google Identity Services' token model, shows incremental consent from the
Settings export action, and creates or replaces the contents of one `JIEN export`
spreadsheet with fixed `Workouts` and `Nutrition` tabs.
